# Raw JSON-RPC exchange against the `claims-system` server, hand-annotated

Captured by `scripts/capture_wire.py`, a minimal client that speaks the MCP stdio
transport directly (newline-delimited JSON-RPC 2.0 messages over the server
subprocess's stdin/stdout) with no SDK client wrapper, so every field below is
exactly what went over the wire. Raw messages are in `wire.json`.

## 1. `initialize` request (client -> server)

```json
{"jsonrpc": "2.0", "id": 1, "method": "initialize", "params": {...}}
```

- `jsonrpc` - protocol version tag for JSON-RPC 2.0 itself, fixed on every message.
- `id` - request id `1`; the server must echo this back on its response so the client can match them up.
- `method` - `"initialize"`, the first call any MCP session must make, before any tool is visible.
- `params.protocolVersion` - the MCP spec version this client speaks (`2025-06-18`); lets client and server negotiate compatibility.
- `params.capabilities` - empty here because this hand-rolled client declares none (no sampling, no roots) - a real client would list what it supports.
- `params.clientInfo` - identifies the client (`wire-capture-client`) to the server, for logging/debugging on the server side.

## 2. `initialize` response (server -> client)

```json
{"jsonrpc": "2.0", "id": 1, "result": {...}}
```

- `id` - echoes `1`, confirming this answers the initialize request.
- `result.capabilities` - what the server supports: `tools`, `resources`, `prompts`, each with `listChanged` (whether it will push a notification if its list changes later) - all `false` here since this server's tool list is static.
- `result.protocolVersion` - the version the server actually agreed to speak back.
- `result.serverInfo` - `{"name": "claims-system", "version": "1.0.0"}` - literally the `MCPServer(name=..., version=...)` values set in `app/mcp_servers/claims_system_server.py`.

## 3. `notifications/initialized` (client -> server)

```json
{"jsonrpc": "2.0", "method": "notifications/initialized"}
```

- No `id` - this is a *notification*, not a request; the protocol never sends a response to it. It's the client's "handshake is done, go ahead" signal, required by MCP before any other call.

## 4. `tools/list` request (client -> server)

```json
{"jsonrpc": "2.0", "id": 2, "method": "tools/list", "params": {}}
```

- `method` - the discovery call this whole task is built around: asks the server to enumerate what it can do, instead of the client hard-coding tool names.
- `params` - empty; this SDK version supports pagination params here but this server has few enough tools not to need it.

## 5. `tools/list` response (server -> client)

```json
{"jsonrpc": "2.0", "id": 2, "result": {"tools": [...]}}
```

- `result.tools` - a list of 2 tool objects, each with:
  - `name` - the identifier the model will call (`get_claim_status`, `get_adjuster_note_history`).
  - `description` - the tool's docstring in `claims_system_server.py`, verbatim. This is the text an LLM host would hand to the model as the tool's prompt-facing description.
  - `inputSchema` - JSON Schema for the tool's arguments, auto-generated by the SDK from the Python function signature (`claim_number: str`). Note the `title` fields (`"Claim Number"`, `"get_claim_statusArguments"`) - these are pydantic's auto-generated titles, not something either server author wrote by hand.

## 6. `tools/call` request (client -> server)

```json
{"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": {"name": "get_claim_status", "arguments": {"claim_number": "CLM-2027-00201"}}}
```

- `params.name` - which discovered tool to invoke - must exactly match a name from the `tools/list` response above.
- `params.arguments` - the tool's actual input, shaped to match that tool's `inputSchema`.

## 7. `tools/call` response (server -> client)

```json
{"jsonrpc": "2.0", "id": 3, "result": {"content": [{"type": "text", "text": "{...}"}], "isError": false}}
```

- `result.content` - a list of content blocks (MCP supports text/image/audio/resource blocks); here one `text` block whose `text` is a JSON string (`{"claim_number": "CLM-2027-00201", "status": "denied"}`) - the tool's actual return value, serialized.
- `result.isError` - `false`; if the tool had raised or returned an error result, this would be `true` and the client/host is expected to surface it to the model as a recoverable message, not crash.

## Where the model call happens, and where it does not

**The model is never called anywhere in this exchange.** Every message above is a plain
JSON-RPC round trip between the client script and the `claims-system` server subprocess -
no Gemini/LLM API call happens during `initialize`, `tools/list`, or `tools/call`. The model
only enters the picture one layer up, inside `app/mcp_agent/agent.py`'s `run()` loop, where
`self.client.models.generate_content(...)` is called with the *discovered* tool declarations
attached - the model decides *which* tool to call and with *what arguments*, but the actual
`tools/call` JSON-RPC request shown above is issued by the client/host code after the model
returns a function-call, and the server that executes it has no idea an LLM was involved at all.
